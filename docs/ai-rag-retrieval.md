# 给 Agent 加语义检索（RAG）：实现记录

> 目标：让 Agent 能用「意思」找笔记，而不只是拿关键词做子串匹配。
> 本文记录最终落地的实现、当时的取舍依据、以及已知的失败模式。
> 上游文档：[`ai-notes-agent-plan.md`](./ai-notes-agent-plan.md)（笔记工具的落地）。

## 1. 这条链路分四层，别把它们混为一谈

排查和讨论时最容易出错的，是把不同层的东西当成二选一。实际上它们各管各的：

| 层 | 职责 | 本项目的选择 |
| --- | --- | --- |
| **接口层** | Agent 怎么触发检索 | 新增 `search_my_notes` 工具 |
| **编码层** | 文本 → 向量 | SiliconFlow 的 `Qwen/Qwen3-Embedding-0.6B`（1024 维） |
| **检索层** | 怎么算谁最像 | 余弦相似度，取 top-k |
| **存储层** | 向量放哪、要不要建索引 | `NoteChunk` 表存二进制，**不建向量索引** |

关键：**光有存储层没有接口层是白做的** —— 向量乖乖存好了，但 Agent 根本不会去查。

### 为什么独立成 `rag` 模块，而不是塞进 `ai`

因为 `notes` 也要用它（保存笔记后重建索引）。放 `ai` 里会让 `notes` 反向依赖 `ai` ——
项目里已经因为同样的问题把 `RateLimitService` 从 `ai` 挪到了 `common`。

依赖方向是单向的：`notes → rag ← ai`，而 `rag` 只依赖 `PrismaModule`。
**`rag` 绝不能反过来依赖 `NotesModule`**，否则直接成环。

## 3. 为什么不装 pgvector（这一节最该看）

结论：**实测之后发现不需要**。

### 3.1 三条路都不划算

Windows 上 pgvector **没有官方预编译包**，只能三选一：

| 方案 | 代价 |
| --- | --- |
| 源码编译 | 要 Visual Studio C++ 工具链（3~7 GB），而本机 C 盘只剩 8.5 GB |
| Docker `pgvector/pgvector` 镜像 | 得把数据迁进容器，或维护两个库 + 处理一致性 |
| conda-forge | 得先装 Anaconda |

另外本机 Postgres 是**官方便携版**（`D:\postgresql-18.3-2-windows-x64-binaries\pgsql`），
不是安装版 —— 网上那些 `set PGROOT=C:\Program Files\PostgreSQL\18` 的教程路径对不上它。

### 3.2 于是实测了「根本不用它」这条路

1024 维，Node 里暴力算余弦：

| 条数 | 内存 | 单次全量检索 |
| --- | --- | --- |
| 1,000 | 3.9 MB | 2.0 ms |
| 5,000 | 19.5 MB | 9.3 ms |
| 10,000 | 39.1 MB | 16.8 ms |
| **20,000** | 78.1 MB | **35.2 ms** |

**2 万条只要 35 ms。** 按每块 400 字算，2 万块 ≈ 几千篇笔记 —— 个人场景到不了。

顺带一个可以省掉的优化：预先把向量归一化、只算点积，实测**只快 1.1~1.4 倍**。
瓶颈在内存访问而不是乘法，所以没必要多维护一份归一化副本。代码里就没做。

### 3.3 什么时候该回头装 pgvector

出现下面任一条再考虑，**不是现在**：

- 单个用户的向量超过 10 万条
- 需要在 **SQL 层**把向量检索和业务条件联合过滤（例如 join 权限表）
- 多进程 / 多实例要共享同一份向量索引

## 4. 数据模型与切块

### 4.1 `NoteChunk`

```prisma
model NoteChunk {
  id        String   @id @default(cuid())
  noteId    String
  userId    String   // 检索必须按它过滤
  seq       Int      // 块在笔记内的序号
  title     String   // 所属小节标题，会和正文拼一起编码
  content   String   // 块正文
  embedding Bytes    // Float32Array 原始字节：1024 维 = 4096 字节
  createdAt DateTime @default(now())

  note Note @relation(fields: [noteId], references: [id], onDelete: Cascade)

  @@index([noteId])
  @@index([userId])
}
```

两个值得说的设计点：

- **`embedding` 存二进制，不存数字数组**。后者要序列化成 JSON 文本，体积是二进制的 3~5 倍。
  代价是读写都要做 `Float32Array` 转换，而且**必须检查 `byteOffset` 是不是 4 字节对齐** ——
  Node 的 Buffer 有时来自共享内存池，不对齐时 `new Float32Array(buf.buffer, buf.byteOffset, …)`
  会直接抛 "start offset should be a multiple of 4"。见 `vector.ts` 的 `decodeVector`。
- **`title` 单独存一份**。一个 400 字的块脱离全文后常常看不出在讲什么，
  小节标题是唯一能提供上下文的线索，所以会和正文拼在一起送去编码。

### 4.2 切块策略

先按 Markdown 标题（`#` ~ `####`）切，超长的再按字数硬切。上限 400 字、下限 30 字。

不按字数一刀切，是因为**标题边界天然就是语义边界**；硬切出来的块常常从句子中间开始，
检索质量明显更差。低于 30 字的块直接丢弃 —— 多半是「# 标题」这种空壳，留着只稀释结果。

## 5. 什么时候重建索引

| 时机 | 处理 |
| --- | --- |
| 新建笔记 | 异步重建该篇 |
| 改标题 / 正文 | 异步重建该篇（**只改置顶不重建** —— 白跑一次 embedding 是浪费） |
| 删除笔记 | 显式清掉该笔记**及整棵子树**的块 |
| 移动笔记 | 不动。不影响被检索的内容 |
| 换 embedding 模型 | **必须全量重建** |

写操作后重建有三条硬约束，缺一不可（`notes.service.ts` 的 `reindexLater`）：

1. **不 await** —— 保存笔记的响应不该等一次 embedding 调用（几百毫秒到几秒）；
2. **失败只记日志** —— 索引是派生数据，它挂了不该让「保存成功」变成报错；
3. **必须 `.catch()`** —— 被 void 掉的 Promise 一旦 reject 就是 unhandledRejection，
   在 Node 里足够把进程带走。

### ⚠️ 换模型时务必全量重建

`EmbeddingService` 里有维度校验、不匹配会直接抛错，但它**只防得住"新写入的"**。
库里存量的旧维度向量不会报错 —— 余弦相似度照样算得出一个数字，只是完全没意义，
检索结果会变得莫名其妙。所以换模型 = 改 `EMBEDDING_DIMENSIONS` + 跑一次全量重建。

全量重建用 `backend/test/index-notes.cjs`：存量笔记不会被写操作钩子覆盖，
第一次上线也要靠它兜底。

索引侧没有"软删除"这一说 —— 切块是纯派生数据，删除就是物理删，
不像笔记那样需要留痕。

## 6. 工具：`search_my_notes`

### 6.1 和 `list_my_notes` 的分工（两个都留，不是替代）

| | `list_my_notes` | `search_my_notes` |
| --- | --- | --- |
| 匹配方式 | 字面（`contains`） | 语义（余弦） |
| 适合 | 用户给了明确的词；要列全部 | 用户描述的是「意思」，如「上次那篇讲卡顿的笔记」 |
| 确定性 | 高 —— 给什么词就搜什么 | 低 —— 结果取决于向量空间 |
| 代价 | 一次 SQL | 一次 embedding 调用 + 内存排序 |
| 工具超时 | 10s | 20s（多一次上游调用） |

**保留两者的理由**：字面匹配在「就是这个词」时更精确、更可预期；
语义检索只在「换个说法」时才发挥优势。实测里模型自己会把两个都调一遍做交叉验证。

> 顺带一个反直觉的实测结论：`contains` 的问题**不是搜不到，而是不会排序** ——
> 四个测试查询分别命中 28 / 13 / 51 / 10 个块，内容都在，但顺序毫无相关性依据，
> 用户不知道该看哪条。语义检索首先补上的是**排序**能力。

### 6.2 `userId` 过滤是硬要求

```ts
const rows = await this.prisma.noteChunk.findMany({
  where: { userId, note: { deletedAt: null } },   // 两个条件都不能省
});
```

- 少了 **`userId`**：会把别人的笔记片段召回给当前用户。这是 RAG 里最容易出的安全事故，
  而且它**不报错** —— 只是"悄悄多返回几条"，不专门查就发现不了。
- 少了 **`note.deletedAt`**：笔记走软删除，`NoteChunk` 上的 Cascade 不会触发，
  已删笔记的块还在库里，不 join 回来过滤就会**搜出已经不存在的内容**。

工具侧还有第二道防线：`userId` 由工厂闭包注入，模型无法通过参数指定别人的 id。

## 7. 已知的失败模式（别指望它万能）

### 7.1 查询词与答案零重叠时会失手

在 901 块的真实文档语料上测过 4 个查询，其中一个是明确的失败案例：

| 查询 | 正确答案所在 | 纯向量排名 | 混合检索排名 |
| --- | --- | --- | --- |
| 消息区与输入框没对齐 | 边距对齐那一节 | **第 1** | 第 1 |
| 多步骤任务会不会中途断 | `MAX_ITERATIONS` 那一节 | **第 1** | 第 2 |
| 会不会把笔记保存成两遍 | 超时但已写入那一节 | 第 22 ❌ | 第 28 |
| 为何不能绕开逻辑直接操作数据库 | 走 NotesService 那一节 | 第 24 | **第 1** |

失败的那个很典型：问「保存成两遍」，答案是「超时但已写入」——
**两者一个词都不重合**，而查询里的"保存 / 笔记"把向量拉向了另一个更大的主题
（讲"两条保存路径"的块），把正确答案挤到第 22 名。

试过加中文 bigram 关键词分做混合检索，**没救回来**（22 → 28 名），
因为 bigram 同样把"保存笔记"主题的块推高了。对症的办法是：

- **rerank**：先多召回（top-50）再用 `Qwen3-Reranker` 精排
  —— ⚠️ **已实测，效果不稳定，暂未接入，见 §9.1**
- **查询改写**：让 LLM 先把「保存成两遍」扩写成「重复写入 / 超时 / 重试」再检索

### 7.2 长文档会污染排名

另一组对照实验：把一篇 2131 字的简历放进语料后，
「改一处、多个组件跟着更新」的 top-1 被简历抢走（0.465）——
因为它塞满 Pinia、多语种、性能优化等技术名词，跟任何技术问题都"沾边"。

**去掉那篇之后，top-3 全部变成正确的 Vue 块**（0.443 / 0.434 / 0.429）。
所以这不是数据个例，是**长文档 + 多主题**的通用问题：
落地时要么把长文按标题切细，要么对超长文档单独降权。

### 7.3 语料质量决定上限

RAG 不会凭空创造内容。落地当天的真实情况是：13 篇笔记里 7 篇内容完全重复、
8 篇正文 ≤7 字，真正有内容的只有 3 篇。**这个体量下 `contains` 其实够用** ——
候选太少，用户自己翻两下就看完了。

所以结论是：**先把管道搭好，等笔记长起来自然受益**，
而不是为了 RAG 提前接一堆复杂度。

## 9. 调优：rerank 试过了，**没接**（附理由）

### 9.1 rerank 实测（2026-10-12）

接口可用：`POST https://api.siliconflow.cn/v1/rerank` + `Qwen/Qwen3-Reranker-0.6B`，
返回 `{results:[{index, relevance_score}]}`，打分很干净（相关 0.9986 vs 无关 0.0009）。

但在真实语料上**效果不稳定**（1135 块，粗召回 50 条后精排）：

| 查询 | 纯向量 | rerank 后 |
| --- | --- | --- |
| 为何不能绕开逻辑直接操作数据库 | 第 29 | **第 4** ✅ |
| 会不会把笔记保存成两遍 | 第 29 | 第 7 ⚠️ |
| 多步骤任务会不会中途断 | 第 3 | **第 12** ❌ 变差 |

**4 个里只有 1 个进前 5，还有 1 个把原本排对的结果推后了。**
所以**没有接进 `NoteSearchService`** —— 证据不足，装了反而可能让现有表现变差。
脚本留在 `backend/test/verify-rerank.cjs`，等评测集建好后可以重跑。

### 9.2 为什么这次给不出可靠结论

**临时挑几个查询做评测，本身就不成立。** 这次暴露的三个问题：

1. **语料切法前后不一致**（上次 901 块、这次 1135 块），两次数据根本不可比
2. **`expect` 用标题字符串匹配不可靠** —— 同一件事在文档里常有多处表述
   （§7.1 就踩过一次：按标题判定会误报失败）
3. **样本太小**（4 个查询），且查询是临时想的、不是用户真实会问的

**要真正做检索调优，先得有这套东西**：固定的语料快照 + 固定查询集 +
人工标注的正确答案 + 可复现的指标（recall@k / MRR）。
**在这之前调优是盲调。**
